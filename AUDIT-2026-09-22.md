# 4uStream Repository Audit — 2026-09-22

## Scope
Audited the supplied ZIP: Next.js 15 / React 19 / Firebase 4uStream web project.

## Confirmed architecture
- Next.js App Router
- Firebase Authentication + Firestore + Storage
- Client-side content queries with Firestore rules
- Admin console for channels, media, episodes, film parts and ads
- Video / HLS / iframe player modes
- PWA manifest + service worker
- Badini / English / Arabic translation foundation

## Immediate fixes applied in this cleaned copy
1. Removed `auth-users.json` from the project package. It contained Firebase Auth export data including password hashes/salts and should not be committed to a repository.
2. Added `auth-users.json` to `.gitignore` so it is not accidentally committed again.
3. Fixed a playback-resume storage bug in `src/components/StreamPlayer.tsx`: the key was written literally as `4u-progress:${resumeKey}` instead of using the resume key value.
4. Fixed the admin delete type so the existing Film Parts manager can call the delete function for `parts` without a TypeScript type mismatch.

## Important issues found for the next development pass
### 1. Email verification flow
The signup flow creates users as `status: active` before Firebase email verification is actually enforced. The custom verification API also has no visible rate limiting. This should be redesigned before production.

### 2. Translation coverage
The code currently defines only Badini, English and Arabic. Sorani is not yet a real translation option, and many UI strings are hard-coded instead of going through the translation system.

### 3. Admin content model
The current admin UI supports channels, media, episodes, film parts and ads, but it is still a foundation rather than the full content studio requested. Poster/thumbnail upload is present for some entities; episode thumbnail upload is not yet part of the episode form.

### 4. Performance
Several pages fetch complete `channels` / `media` collections from Firestore. This is acceptable for a small catalog but will become expensive and slower as the catalog grows. The next pass should add pagination/limits, query indexes where needed, caching, and avoid repeated full-collection reads.

### 5. Images
The project uses many raw `<img>` elements. This works, but image sizing, responsive loading, compression and lazy loading should be standardized to reduce mobile bandwidth and CPU usage.

### 6. Player performance
The player is isolated to the watch/live page, which is good. HLS uses dynamic `hls.js` loading, also good. The next pass should further ensure no player/stream is initialized on cards or the home page.

### 7. Security / validation
Firestore rules provide the main authorization boundary, which is good. The admin UI should still validate URLs, content fields, file types and sizes before writes. The public verification endpoint should receive rate limiting and abuse protection.

### 8. Build verification
A full `npm ci` could not complete in the audit environment within the available execution window, so a production `next build` was not claimed as verified. Static source inspection was completed.

## Recommended build order
1. Stabilize and build-test the current codebase.
2. Fix authentication/email verification and admin authorization workflow.
3. Build the complete mobile-first Admin Content Studio.
4. Add episode thumbnails and richer movie/drama metadata.
5. Implement external embed URL support cleanly for authorized providers.
6. Add Sorani and move remaining UI strings into translations.
7. Optimize Firestore reads, images, caching and player lifecycle.
8. Add VIP/payment/advertising modules after the core catalog is stable.
